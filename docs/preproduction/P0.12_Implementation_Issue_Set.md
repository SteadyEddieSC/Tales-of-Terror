# P0.12 Implementation Issue Set

## Decision

Drowned Harbor is conditionally authorized in principle for a future isolated prototype. Runtime execution remains blocked pending explicit user reopening and the remaining unlock gates in `drowned_harbor_prototype_authorization_v1.json`.

This issue set is implementation-ready planning, not implementation authorization.

## Parent

### #79 — P0.12: Drowned Harbor isolated prototype authorization and issue set

Owns the P0.12 decision, documentation/tooling package, child issue linkage, and release closure.

Close only after P0.12 merges to protected `main` and all child issues remain accurately blocked.

## Child issue order

### 1. #80 — Prototype isolation boundary

Establish the dev-only identity, fail-closed entry, normal Tale Library exclusion, production catalog integrity, and ordinary-export exclusion.

This issue must be completed first. No other prototype issue may bypass its isolation boundary.

### 2. #81 — Deterministic state and projection fixtures

Create synthetic source/result revisions and representative projections for the governed prototype traces.

Depends on #80. It supplies data and event identity to the remaining interaction proofs.

### 3. #82 — Low-Tide shared-screen prototype shell

Create the controller-first public board shell for `DH-UI-003` / `DH-IS-003` using synthetic fixtures.

Depends on #80 and #81. It proves public projection, focus, stable-seat ownership, captions, persistent text, and the cool-dark non-muddy placeholder direction.

### 4. #83 — Bellhouse decision and invalid-action recovery

Create one exactly-once public commitment flow plus fail-closed stale, wrong-seat, and unavailable-action recovery.

Depends on #80–#82. It proves command guards, preview/cancel non-mutation, event identity, deterministic recovery, and focus restoration.

### 5. #84 — Controlled-private neutral shield proof

Create the shared neutral shield, authorized private-surface abstraction, acknowledgement/confirmation boundary, clearing behavior, and safe unavailable-surface fallback.

Depends on #80, #81, and #83. It may not add a production Companion endpoint or make a privacy/security certification claim.

### 6. #85 — High Water deterministic transformation proof

Create the committed before-state, exactly-once transformation, skip-equivalent presentation, changed-category summary, and transformed-board projection.

Depends on #80–#83. It does not include final water simulation, final cinematics, final assets, or Last Light completion.

### 7. #86 — Prototype automation and export exclusion

Create exact-head deterministic, privacy, replay, deadlock, catalog-integrity, and export-exclusion evidence for the implemented prototype slice.

Depends on #80–#85. It may not suppress issue #44 or substitute for issue #39 human evidence.

## Shared acceptance rules

Every future child issue must:

- begin only after explicit user reopening;
- use a clean branch from then-current protected `main`;
- preserve Lantern House as the sole production Tale;
- keep `game/data/tales/tale_catalog_v1.json` unchanged;
- preserve P0.10 storyboard and P0.11 interaction-trace obligations;
- use synthetic/dev-only identity and fixtures;
- fail closed on stale state, wrong authority, invalid target, unavailable private surface, or malformed projection;
- preserve stable-seat identity and evolved state;
- keep private payloads out of public display, audio, captions, transcript, replay, diagnostics, mirroring, and public history;
- define exact automated checks before merge;
- state that automated evidence is not human controller, television, accessibility, privacy, fun, pacing, fairness, or balance evidence.

## Shared prohibitions

No child issue may independently authorize:

- a production Tale package, provider, catalog entry, or Tale Library entry;
- a public or ordinary portable playable Drowned Harbor export;
- final art, audio, voice, localization, legal title, store page, rating, release date, or marketing promise;
- issue #44 suppression or reinterpretation;
- issue #39 closure or replacement by automation;
- a claim that Drowned Harbor is complete, playable in production, accessible, private, secure, fun, fair, balanced, or human-validated.

## Replanning rule

A child issue may be split only when the split preserves the parent objective, source authorities, blocked status, dependency ordering, production isolation, and acceptance boundaries. Broadening into a complete Tale, full vertical slice, production package, online service, or public build requires a new authorization decision rather than an issue edit.
